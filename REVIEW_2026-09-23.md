# Independent review — 2026-09-23

_Outside review by Claude, read-only. It covers the handoff docs, the reports in
`work/` and `outputs/`, the collectors and the scoring code. No code, data,
schedule or `.env` was changed. The 2.4 GB database was not opened._

## Verdict

The engineering is in good shape. It runs, it is tested (69 tests), the database
is protected, writes are additive and idempotent, browsing is read-only, and the
matching rules are documented and consistent. The Codex sessions were careful.

The biggest risks are **not in the code**. They are (1) how fair the comparison is
scientifically, (2) whether the results mean anything statistically, and (3) how
fast storage is growing. Performance work is already under way and well planned.

## 1. Scientific fairness (highest priority)

**a. Yr has a "home advantage" at these stations.** For the first ~2–3 days, Yr
comes from MET Nordic, which is post-processed and bias-corrected using
observations. Those include the same Frost/MET stations used here as the answer
key. WeatherNext has no station-level correction. So Yr's lead at short range
partly reflects that it is tuned to these exact stations. That is fine if the
question is "what's best for Norwegians using Yr?", but it is not a pure model
comparison. *Improve:* state this caveat in SCORING.md and the dashboard. Consider
tagging stations as "used in MET post-processing" or not, or adding a few
independent stations (e.g. Netatmo is *also* assimilated, so not those) if any
exist.

**b. Yr's "issue time" is not a model run time.** `met_forecast.py` stores
`meta.updated_at` as `issued_at`. Yr refreshes about every hour, so its "lead" is
measured from the latest refresh. WeatherNext's lead is measured from its
initialization, which is published hours later. That is why the reports see
WeatherNext leads about 2.4 h shorter. The ≤3 h gap rule hides this, but it gives
the two sides different definitions of lead. *Improve:* add a second, user-view
comparison, "the forecasts you could actually see at time X". Pair by retrieval
time, measure lead from retrieval for both, and keep the current init-based view.

**c. Ensemble mean vs single forecast.** WeatherNext is scored on its *ensemble
mean*. Averaging smooths out extremes, which lowers MAE, especially at long leads
and for rain amounts. Yr is a single post-processed value. *Improve:* also score
the WeatherNext **p50 (median)**, which is already stored, as a second line.
Where the mean and p50 give different answers, this effect is at work.

**d. Yr's own uncertainty is not collected.** The collector uses the `/compact`
endpoint. The `/complete` endpoint adds Yr's p10/p90 for temperature and wind,
plus precipitation min/max/probability. *Improve:* switch the collector to
`/complete` (additive columns). Then both providers' uncertainty bands can be
checked for calibration: does the observation fall inside p10–p90 about 80% of
the time? That is P2 on your roadmap, and it can only be done for WeatherNext
today.

## 2. Statistical meaning

You have about 3 weeks of data from 50 stations. Errors are strongly correlated
across nearby stations and neighbouring hours. So "1,603 shared samples" behaves
like far fewer independent ones. The docs rightly say "no winner claim", but the
dashboard shows no uncertainty on the MAE differences. *Improve:* add a
**block-bootstrap confidence interval** (resample whole days) on the
"WN − Yr MAE" difference per lead bucket. Show "not significant" when the
interval crosses zero. That turns the cautious wording into a number, and it
tells you when enough data has come in.

## 3. Storage growth (act within weeks)

The architecture review estimates ~1.5 M WeatherNext rows/day, roughly **100 GB/year**,
with no retention policy. `data/weather.db` is already 2.4 GB. *Improve (pick one):*

- Keep full percentiles only for scored variables (temperature, wind, precipitation).
  Store pressure and u/v as mean only.
- Thin long leads: hourly to 72 h, then 3-hourly (or 6-hourly) to 360 h. Your long-range
  scoring only uses nominal 3/5/7/9-day targets anyway.
- Move closed months to a monthly archive DB file, which keeps the live DB small and
  backups practical.

Decide this before the performance/index work, since indexes add disk too.

## 4. Documentation (your .md system)

Keeping everything in .md files works: any new session can pick up the project.
The weak spots:

- `PROJECT_STATUS.md`, `NEXT_STEPS.md` and `WORK_STATUS.md` (32 KB) are **append-only
  logs**. Each has dated sections that partly contradict older ones. For example,
  README still says rain "is stored but not yet scored". NEXT_STEPS both says
  "precipitation scoring disabled" and "complete".
- *Suggest:* keep `PROJECT_STATUS.md` = **current state only** (≤1 page, rewritten
  each time). Keep `NEXT_STEPS.md` = **open items only** (delete done items). Move the dated
  history into a single `CHANGELOG.md`. Keep `DECISIONS.md` and `SCORING.md` as they are.
  They are the most valuable files.
- Fix the stale README line about rainfall.

## 5. Housekeeping

- The status-optimization commit is local only. Push it when ready.
- `work/` holds ~20 MB of CSVs/logs and duplicate files (e.g. identical
  `ui-tests.log` / `checkpoint-ui-tests.log`). It is ignored by Git, which is fine.
  Keep the provenance manifests (`work/temperature-backfill/first-run.json`,
  `second-run.json`) and archive the rest.
- `scoring/scorer.py` still holds the legacy hour-floored join (`strftime` on
  `observed_at`). The docs say it is off the dashboard path. Mark it deprecated or
  remove it, so no future session reuses it by mistake.
- `app.py` is 968 lines. That is fine for now. The architecture review rightly says
  not to refactor it for looks alone.

## Findings, in priority order

### P1 — Public history bypasses the forecast-value publishing policy

`cloud/summarize.py:268` gates station-chart JSON only. `cloud/store.py` writes
scored days in plain gzip, and `.github/workflows/collect.yml:72` commits those
files to the public repository. The public 27 Sep file was fetched and checked:
4,394 rows, including 4,151 non-null `wn_t` values, while live metadata says
`publish_forecast_values: false`. Other WeatherNext statistic columns also form
part of the scored schema.

This contradicts the current DECISIONS policy to withhold past forecast values
pending clarification. It is a verified implementation/policy mismatch, not a
conclusion that the licence prohibits those past values. Decide how private
scored storage and public aggregate exports should be separated, or explicitly
resolve the policy. Encryption of pending state does not address public history.
Any action on already-published history needs a separate decision; this review
did not alter or remove it.

### P1 — Observation outages can permanently discard a day's forecasts

`cloud/score.py:156–160` writes a ready day, marks it finalized, and drops its
pending forecasts even if no observations were available. `cloud/run.py` calls
finalize after Frost errors, and the workflow does not use strict mode.

Disposable reproduction: one pending forecast for 27 Sep, no observations,
finalization at 28 Sep 07 UTC. Result: an empty scored day, zero pending rows,
and 27 Sep marked finalized. Later observations cannot repair it automatically.
Delay finalization after source failure or inadequate day coverage; retain the
pending forecasts until a deliberate completeness/timeout decision. Merely
adding `--strict` does not fix this: its exit happens after finalization.

### P1 — State restore failures are treated as a fresh installation

`.github/workflows/collect.yml:40–42` falls back to `mkdir -p state` after any
clone failure. A network/authentication error can therefore produce an empty
state, followed by normal collection and a force-push replacing the existing
state branch. Distinguish a deliberately empty first run from a failed restore;
abort on restore failures. This path was identified in code, not induced live.

### P1 — Pruned state is published before its scored history is secured

The workflow pushes working state at line 65, then commits/pushes scored days at
lines 72–76. Finalization has already removed those days' pending forecasts.
If the history commit/rebase/push fails after the state push, the next run sees
the days finalized but main lacks their scored files. There is no automatic
recovery from that committed state. Secure the immutable scored files before
publishing the pruned state; test interruption between the two writes.

### P2 — Failure reporting needs a persistence-safe design

`cloud.run all` currently returns success after reported source errors unless
`--strict` is supplied. The site health line helps, but green Actions runs can
hide partial failures. Do not simply add `--strict` to the current workflow:
its nonzero exit would skip later state/history saves and health deployment.
Preserve successful collection and publish health first, then mark the run
failed, alongside the finalization guard above.

## Verdict

The core recommendation is right and should be approved: **start saving the complete Yr
response twice a day, now.** It is the only data in the project that can never be recovered
later. It needs no extra API calls and costs about 0.33 GB/year. The plan is careful and its
code claims are accurate. However, it is too large to approve as written, and some parts are
more complicated than a one-person project needs. The risk is that the first milestone (M1)
never ships, while Yr data that can't be replaced is lost every day.

## Checked and correct

- Numbers are rounded to three decimals at the history writer (`store.py:77`).
- State publication commits only `pending.csv.gz`, `obs.csv.gz` and `meta.json` (`persistence.py:140`).
- The collection gate counts a run as a success if **any** source returned rows (`health.py:63`).
- Row selection prefers rows that have both Yr and WeatherNext *temperature*, for every variable.
  IFS/AIFS are left-joined, so rows with only ECMWF are dropped (`score.py:90–106`).
- `fetched` is the job start, before any request is made (`run.py:28`).
- The MSLP coverage check (35/49 stations, 8-station low-level pilot) is real evidence and useful.
- Corrections to my earlier suggestions, which I accept: MSLP does *not* fully isolate how good a
  model is, and the four products are not a clean "AI vs physics" experiment. Describe them as
  products.

## Changes before approval

1. **Drop the durable retry spool from M1.** The slot window is already the retry: an 08:30–13:00
   UTC slot spans about two collections, so if one fails, the next can capture. If the window
   closes, write a missing-slot record. This removes the hardest part of M1 (a change to
   persistence) without losing anything important.
2. **Store M1 in a separate private GitHub repo**, not an object-storage bucket. At about
   0.33 GB/year it fits for years. It also lives off this PC. Choose object storage only when the
   WeatherNext/ECMWF expansion (3–5 GB/year) is approved.
3. **Keys:** a separate archive key doubles the ways keys can be lost. Either reuse an escrowed
   key, or escrow both keys together in the same secure place before activation.
4. **Remove three-decimal rounding from the loss list.** 0.001 °C, mm or m/s is not a meaningful
   loss. Rounding is fine for scored history.
5. **Decide the minimum for M1:** Yr raw responses, slot policy and simple manifests. Postpone
   observation vintages, the six-clock schema beyond the timestamps actually received, and RPO/RTO
   targets (how much data and downtime a failure may cost) until there is a reason to need them.

## Missed quick wins (no archive needed)

- **Gate fix.** Record per-source success, so a WeatherNext outage can't hide behind Yr rows. Small and separate.
